# Rhombus Webhook Payload Reference

Rhombus sends two kinds of webhooks. They differ in how you configure them, the body they send, and the signature header. Docs: https://developer.rhombus.com/webhooks

| | Organization webhooks | Rule webhook actions |
|---|---|---|
| Configured in | Console **Settings → Integrations & Developer Resources → Webhooks** (Trigger Type **Activity** or **Diagnostic**), or `POST /api/integrations/webhooks/updateWebhookIntegrationV2` | The webhook action on a rule (`POST /api/rules/createRule`, `POST /api/rules/updateRule`) |
| Secret | One per URL. Shown in the Console's **Webhook Secret** column; returned as `webhookSecret` when you add a `webhookUrl`; listed by `POST /api/integrations/webhooks/getWebhookIntegration` under `orgIntegrationV2.activityWebhooksV2` / `diagnosticWebhooksV2` | One per URL, generated by Rhombus. Returned as `webhookSecrets` (URL → secret) by `createRule` / `updateRule`. A secret sent in the request is ignored. |
| Signature header | `x-rhombus-signature-sha1` | `x-rhombus-signature-sha256` (only when the action has a secret; actions without one are sent unsigned) |
| Algorithm | HMAC-SHA1 | HMAC-SHA256 |
| Counts as delivered | Any `2xx` | `200` or `202` only |

## Envelope (both kinds)

- HTTP method: `POST`
- Headers: `Content-Type: application/json`, plus the signature header above. There is no delivery-ID header.
- Body: compact UTF-8 JSON.
- Signature: lowercase hex HMAC of the **raw request body bytes**, keyed with the webhook secret string used as-is (its UTF-8 bytes; the secret is a 22-character base64url string, so don't decode it). Only the body is signed; there is no signed timestamp.
- Don't count on redelivery. A failed delivery (non-success status, connection error, or timeout) is recorded as a webhook-failure diagnostic in the organization, not retried. Still de-duplicate by `alertUuid` (organization webhooks) or `uuid` (rule actions).

## Organization webhook body

Fields, in the order Rhombus writes them. Fields that don't apply to an event are omitted.

| Field | Type | Meaning |
|---|---|---|
| `version` | string | Always `"2"` |
| `activityTrigger` | string | Comma-separated activity names that fired an Activity webhook, e.g. `"MOTION_HUMAN"` |
| `diagnosticTrigger` | string | Diagnostic activity that fired a Diagnostic webhook, e.g. `"CAMERA_DISCONNECTED"` |
| `summary` | string | One-line human-readable description (English) |
| `deviceUuid` | string | Device that produced the event |
| `location` | string | **UUID** of the device's location (not a name) |
| `deviceType` | string | Device type name, e.g. `"CAMERA"` |
| `timestampMs` | number | Event time, Unix epoch milliseconds |
| `alertUuid` | string | Alert (policy alert) UUID, when the event created one |
| `diagnosticUuid` | string | Diagnostic event UUID, for diagnostic events |
| `durationSec` | number | Event duration in seconds |
| `thumbnailLocation` | string | Storage region of the alert thumbnail, e.g. `"us-west-2"` |
| `clipLocationMap` | object | Device ID → storage region of each device's clip |

Activity example:

```json
{
  "version": "2",
  "activityTrigger": "MOTION_HUMAN",
  "summary": "Human motion detected on Front Door",
  "deviceUuid": "BBBBBBBBBBBBBBBBBBBBBB",
  "location": "CCCCCCCCCCCCCCCCCCCCCC",
  "deviceType": "CAMERA",
  "timestampMs": 1712345678000,
  "alertUuid": "DDDDDDDDDDDDDDDDDDDDDD",
  "durationSec": 12,
  "thumbnailLocation": "us-west-2",
  "clipLocationMap": { "BBBBBBBBBBBBBBBBBBBBBB": "us-west-2" }
}
```

Diagnostic example:

```json
{
  "version": "2",
  "diagnosticTrigger": "CAMERA_DISCONNECTED",
  "summary": "Front Door went offline",
  "deviceUuid": "BBBBBBBBBBBBBBBBBBBBBB",
  "location": "CCCCCCCCCCCCCCCCCCCCCC",
  "deviceType": "CAMERA",
  "timestampMs": 1712345678000,
  "diagnosticUuid": "EEEEEEEEEEEEEEEEEEEEEE"
}
```

The `summary` strings above are illustrative. Activity names come from `ActivityEnum` and diagnostic names from `DiagnosticActivityEnum` in the OpenAPI spec (`../../rhombus-api/references/rhombus-api.json`). To fetch the alert's details, clip or thumbnail, call the API with `alertUuid` (for example `POST /api/event/getPolicyAlertDetails`).

## Rule webhook action body

The body describes the rule run. Keys are written in alphabetical order; which event lists are present depends on the rule's triggers.

```json
{
  "deviceEvents": [
    {
      "activities": ["MOTION_HUMAN"],
      "deviceType": "CAMERA",
      "deviceUuid": "BBBBBBBBBBBBBBBBBBBBBB",
      "eventUuid": "FFFFFFFFFFFFFFFFFFFFFF",
      "locationUuid": "CCCCCCCCCCCCCCCCCCCCCC",
      "timestampMs": 1712345678000
    }
  ],
  "orgUuid": "GGGGGGGGGGGGGGGGGGGGGG",
  "ruleTriggers": [ { "type": "DEVICE_ACTIVITY_EVENT" } ],
  "ruleUuid": "HHHHHHHHHHHHHHHHHHHHHH",
  "triggeredTimestampMs": 1712345678000,
  "uuid": "AAAAAAAAAAAAAAAAAAAAAA"
}
```

- `uuid` identifies this rule run; use it for de-duplication.
- `deviceEvents` entries can carry more fields depending on the device (for example `durationSec`, sensor readings, or identified faces and vehicles).
- Other triggers populate other lists instead of, or as well as, `deviceEvents` (for example scheduled, lockdown or incoming-webhook events).
- Not every event comes from a camera: check `deviceType` before assuming what `deviceUuid` refers to.

## Signature verification

Read the raw body, pick the header that's present, compute the HMAC with that URL's secret, and compare in constant time. Respond `401` on a missing or bad signature; otherwise return `200` quickly and process asynchronously.

Test vector: secret `AAAAAAAAAAAAAAAAAAAAAA`, body `{"version":"2","summary":"Test webhook"}` → HMAC-SHA1 `7c67f32d7b1320f76fa6d171a1a54dd6808570b6`, HMAC-SHA256 `5d3808f7c72ed8b6e52c12cf3ae13e72667d316178c6110081d58282828b2482`.

### Node (TypeScript)

```typescript
import crypto from 'crypto';

const SIGNATURE_HEADERS: Array<[string, 'sha256' | 'sha1']> = [
  ['x-rhombus-signature-sha256', 'sha256'], // rule webhook actions
  ['x-rhombus-signature-sha1', 'sha1'],     // organization webhooks
];

export function verifyRhombusSignature(
  rawBody: Buffer,
  headers: Record<string, string | string[] | undefined>,
  secret: string,
): boolean {
  for (const [name, algorithm] of SIGNATURE_HEADERS) {
    const value = headers[name];
    const received = Array.isArray(value) ? value[0] : value;
    if (received) {
      const expected = crypto.createHmac(algorithm, secret).update(rawBody).digest('hex');
      const a = Buffer.from(expected, 'utf8');
      const b = Buffer.from(received.trim().toLowerCase(), 'utf8');
      return a.length === b.length && crypto.timingSafeEqual(a, b);
    }
  }
  return false; // unsigned request
}
```

Node lowercases incoming header names, so look them up in lowercase. Use `express.raw({ type: 'application/json' })` on the route so `req.body` is the raw `Buffer`.

### Python

```python
import hashlib
import hmac

SIGNATURE_HEADERS = (
    ("x-rhombus-signature-sha256", hashlib.sha256),  # rule webhook actions
    ("x-rhombus-signature-sha1", hashlib.sha1),      # organization webhooks
)


def verify_rhombus_signature(raw_body: bytes, headers, secret: str) -> bool:
    """headers: a case-insensitive mapping (Flask/Starlette request.headers)."""
    for name, digestmod in SIGNATURE_HEADERS:
        received = headers.get(name)
        if received:
            expected = hmac.new(secret.encode("utf-8"), raw_body, digestmod).hexdigest()
            return hmac.compare_digest(expected, received.strip().lower())
    return False  # unsigned request
```
